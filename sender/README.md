# Sender

Бот на aiogram получает JSON из RabbitMQ и отправляет поле `text` во все группы
и каналы, куда его добавил владелец с `ADMIN_ID`. Заранее указывать чаты не нужно.

## Запуск

Настройки находятся в едином корневом `.env`. Инструкция запуска всех сервисов
через Docker Compose: [README проекта](../README.md).

Добавьте бота в нужные чаты от аккаунта владельца, разрешив отправку сообщений.
В канале боту нужны права администратора на публикацию.

Для локальной разработки из папки `sender`: `uv sync`, затем `uv run python main.py`.
Задайте `RABBITMQ_URL` в окружении с адресом `127.0.0.1:5673` и учётными данными
брокера из общего `.env`.

При добавлении владельцем ID чата сохраняется в локальный `chats.json`. При добавлении
другим пользователем бот сразу вызывает `leave_chat`, не подключая чат к рассылке.
При удалении бота чат исключается. Изменение прав уже добавленного бота список не меняет.
Добавляйте бота от личного аккаунта владельца, не анонимно.
Telegram Bot API позволяет реагировать на добавление, но не запретить само действие.

Список автоматически загружается после перезапуска. Файл `/data/chats.json` в Docker
(постоянный том `sender_data`) или `sender/chats.json` при локальном запуске
создаётся при изменении списка; зависимости и отдельный сервер для хранения не нужны.
Запись выполняется через временный файл с последующей атомарной заменой.
Путь можно изменить переменной `CHATS_FILE`. Запускайте один экземпляр sender на файл.
При повреждении JSON запуск завершится с ошибкой, не перезаписывая сохранённые данные.

Для групп, куда бот был добавлен до первого запуска, владелец может написать
`/register`. Для каналов удалите и снова добавьте бота: пост от имени канала не позволяет
проверить ID владельца. При переносе бота сохраните `chats.json`; при смене владельца
используйте новый файл, чтобы не продолжать рассылку в чаты предыдущего владельца.

Настройки читаются из корневого `.env`, затем из переменных окружения.
`CHAT_ID` парсера и `chat_id` в JSON — источник, они не задают адресатов.

## Доставка

Формат сообщения существующего парсера:

```json
{"chat_id": -1001111111111, "message_id": 42, "date": "2026-09-10T12:00:00+00:00", "text": "Привет!", "entities": [{"type": "bold", "offset": 0, "length": 6}]}
```

Оформление передаётся через `entities`: жирный/курсив, подчёркивание/зачёркивание,
спойлеры, цитаты (включая сворачиваемые), код, ссылки и custom emoji.
Текст не разбирается повторно как Markdown/HTML. Предпросмотр ссылок выключен.
Custom emoji отображаются при наличии соответствующих прав у бота в Telegram.
Не поддерживаемые преобразователем MTProto entities пропускаются с записью в лог;
их текст сохраняется. Старые сообщения очереди без `entities` отправляются как обычный текст.

Используется durable-очередь `telegram_posts`, сообщения обрабатываются по одному.
Если список чатов пуст, сообщение ожидает без подтверждения. После рассылки во все
чаты из списка на начало отправки RabbitMQ получает подтверждение. Чаты, подключённые
позже, получают следующие сообщения; история не пересылается.

При ошибках Telegram повторяется отправка в текущий чат с задержкой. Если бот лишён
права публикации, восстановите права или удалите его из чата при работающем sender,
иначе обработка очереди будет ждать. При остановке до подтверждения сообщение может
прийти повторно, в том числе в чаты, куда оно уже было отправлено.

Некорректный JSON и пустой текст пропускаются с записью в лог. Один элемент очереди
отправляется одним текстовым сообщением (лимит Telegram — 4096 символов).
Медиа, история доставки и защита от дублей не реализованы.
